# Codebase Context — Admin Panel (React)

> **Purpose of this file (read first).**
> This is the **map** of the admin-panel codebase — *what it is, where things live, how data flows, and how it talks to the backend.* It exists so an automated agent can orient itself **before** changing anything.
>
> It is **descriptive**, not prescriptive. For *how you must write code here*, see [`engineering-guidelines.md`](./engineering-guidelines.md).
>
> The API it consumes is the NestJS GraphQL backend — see `../nestjs-graphql/codebase-context.md`. This app is a **pure consumer**: it never talks to a commerce platform or AI vendor directly.

---

## 1. What this system is

A **back-office web app** (React 19) used by a client's **staff** to operate the product: browse the catalog synced from their commerce platform, trigger and monitor **syncs**, manage assets, configure their platform connection and locales, and administer users/roles. (Customers use the separate **designer tool**.)

- **Audience:** internal staff/admins — RBAC-gated (`admin`, `editor`, …).
- **Tenancy:** **one client per deployment** — each client runs its own admin instance and the tenant is fixed by the backend (derived from the JWT). This is **not** a multi-tenant console; there is no in-app tenant switching. (If that changes, add cache-reset-on-tenant-switch + per-tenant RBAC.)
- **Backend:** the NestJS GraphQL API. The admin panel holds **no business logic that belongs server-side** — catalog truth, sync execution, and authorization all live in the backend; this app reads and triggers.
- **Shape:** data-dense — tables, filters, forms, detail panes, dashboards, long-running job status.

## 4. Anatomy of a feature module

```
features/<feature>/
├── components/        # <Feature>Table.tsx, <Feature>Form.tsx, … (+ co-located .test.tsx)
├── hooks/             # use<Feature>.ts (+ .test.ts) — Apollo wiring, derived state
├── graphql/           # operations.ts — typed `graphql()` documents (consumed via Apollo useQuery/useMutation)
├── utils/             # pure helpers (+ .test.ts)
└── types.ts
```

Components are presentational; data access uses **typed `graphql()` documents** (from `src/gql`, generated by the **client-preset**) with **colocated fragments** (`useFragment`); forms use React Hook Form + Zod resolvers.

## 6. How it talks to the backend (the integration contract)

```
React component → generated Apollo hook → Apollo Client → POST /graphql (NestJS)
   • Authorization: Bearer <JWT>     (lib/auth attaches; refresh on UNAUTHENTICATED)
   • Accept-Language: <locale>       (localized content from the backend)
GraphQL errors → read extensions.code (UNAUTHENTICATED / FORBIDDEN / NOT_FOUND / VALIDATION_FAILED / CONFLICT / RATE_LIMITED / INTERNAL)
Long jobs (sync) → subscribe (graphql-ws) or poll jobStatus
```

- **Auth & RBAC:** login mutation; access token in memory (refresh flow), `Authorization: Bearer`. The current user's **roles** (from the backend) drive route guards and action visibility — but the **server enforces** authorization; the UI only hides what the user can't do.
- **Catalog:** products/categories/attributes are **read from the backend** (synced from the platform into Postgres). The admin panel never calls Magento/Shopify; it triggers a **sync** and the backend does.
- **Sync Now:** a mutation enqueues a backend **BullMQ** job and returns a `syncRunId`; the UI then **subscribes/polls** the `sync-run` for progress, counts, and errors.
- **Settings (platform connection):** the platform base URL + **credentials** and the **store-view↔locale** map are written to the backend's per-tenant config. Credentials are **write-only** from the UI (never read back / displayed).
- **Assets:** previews load via backend **signed URLs**; no direct S3.
- **Codegen:** `codegen.ts` uses the **`@graphql-codegen/client-preset`** to generate `src/gql/` (typed `graphql()` + fragment types) from the backend's committed **`schema.gql`** (or dev/staging endpoint — never prod); runs in CI and fails on schema drift.

## 7. Routing & RBAC

React Router v7, lazy + **role-guarded**: a route declares the role(s) it needs; the guard reads the current user's roles and redirects/blocks otherwise. Typical areas: `dashboard`, `catalog`, `sync`, `media`, `users` (admin-only), `settings` (admin-only).

## 8. Data flow (a typical list + action)

```
CatalogPage → useProducts() (generated hook, Relay pagination)
   → TanStack Table (sort/filter/page state in URL)
   → row action (e.g. re-sync) → mutation → Apollo cache update / refetch
SyncPage → triggerSync mutation → syncRunId
   → subscription/poll → live progress UI
```

## 9. Internationalization (i18n) — two layers

The app is multilingual on **two layers**, both driven by **one resolved locale**:

| Layer | What | Owner |
| --- | --- | --- |
| **UI strings we author** | labels, buttons, table headers, tooltips, toasts, empty states, client-side validation hints | **i18next** translation bundles in this repo |
| **Server-returned content** | product/category names, backend error messages | the backend, requested via **`Accept-Language`** (§6) |

- **Where UI translations live:** `src/lib/i18n/locales/<lang>/<namespace>.json`, **namespaced per feature** (`common`, `catalog`, `sync`, `users`, `settings`, …). Components read them via `useTranslation('<namespace>')` → `t('key')` — never inline literals.
- **Single locale source:** `src/lib/i18n` owns the active locale. The **same value** configures i18next *and* is sent as the `Accept-Language` header, so UI chrome and server content always match. The language switcher updates it once; both layers follow. Persisted/detected, **allowlisted** against `VITE_SUPPORTED_LOCALES`, falling back to `VITE_DEFAULT_LOCALE`.
- **Loading:** locale bundles are lazy-loaded per language so the initial bundle stays small.

> So "multilanguage" = **backend localizes content** (Accept-Language) **+ this app localizes its own UI** (i18next bundles). The enforceable rules are in [`engineering-guidelines.md`](./engineering-guidelines.md) §8.

## 10. Testing topology

- **Unit tests** co-located (Vitest + Testing Library); API mocked with **MSW**.
- **Shared infra** in `src/__tests__/`: `setup.ts`, `test-utils.tsx` (renders with Apollo/MSW/router/i18n), `mocks/handlers.ts`, `mocks/fixtures/`.
- **E2E** (Playwright): login + RBAC gating, catalog browse/filter, sync trigger→complete, settings save.
